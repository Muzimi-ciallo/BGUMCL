# BGUMCL Download Engine V2 激进下载核心设计

## 目标

以一次性切换核心路径的方式替换当前下载调度器，使整合包、MOD、Forge、Minecraft 运行库和资源文件共享同一套高吞吐、可恢复的下载引擎。在同一设备、网络和整合包下，三轮冷启动测试的中位总耗时目标为不高于 PCL 的 1.2 倍，并消除最后少量文件长期停滞的问题。

本次只生成本地 Windows 便携实验版，不生成安装版或其他操作系统构建，不推送 GitHub，不创建 Release，不更新远程版本清单。

## 核心切换

- 新引擎统一负责候选源、连接调度、源健康、动态分段、恢复、校验和进度聚合。
- 原下载引擎退出正常调用路径，但在实验验证阶段保留代码级回退入口。
- 前端任务事件、实例导入接口、暂停、恢复、取消和任务组接口保持兼容。
- 不直接复制 PCL 的 VB.NET 实现；复现其持续补充连接、失败任务让出槽位、按剩余工作调度和快速恢复的行为。

## 调度模型

- 自动并发模式从 32 条连接起步，根据两秒吞吐量窗口提升到 64、96，最高 128 条；吞吐量没有收益或错误率升高时回退。
- 手动并发模式尊重用户设置，不突破配置上限。
- 等待退避、熔断或暂停的任务不占用有效传输槽位。
- 调度器持续补充空闲槽位，并允许健康的热点域名借用空闲连接。
- 队列按文件大小和来源交错排序；大文件提前启动，达到 80% 后进入尾部模式，优先处理停滞或剩余量最大的文件。

## 源健康与抢跑

- 健康状态按候选 URL 和当前连接独立维护，域名级状态仅作聚合参考，任何新响应都不能清空其他连接的速度样本。
- 记录 DNS/连接失败、首字节延迟、HTTP 状态、无数据停滞、传输速率、Range 错误和哈希错误。
- 切源必须推进到不同候选；失败候选进入有期限的冷却，不能在同一轮立即重新选中。
- 首字节长期未到达、连接连续无数据或多个窗口持续低速时，可启动一个备用候选抢跑请求；首个产生稳定有效数据的连接获胜，其他连接取消。
- 抢跑具有每文件和全局上限，避免无限放大流量。

## 动态分段与恢复

- 小文件默认单流，避免 Range 开销。
- 8 MiB 以上且明确支持 Range 的文件可以分为 2 至 4 段；64 MiB 以上最多 8 段。
- 分段数量受全局连接预算和当前吞吐量约束，不能挤占尚未启动文件的基本连接。
- 单段失败只恢复该段；服务器忽略 Range、返回异常 Content-Range 或连续分段失败时立即降级为单流。
- 临时文件及分段状态可恢复，完成后先核对长度和 SHA-1，再原子替换目标文件。

## 大陆网络连接策略

- 扩大 HTTP/1.1 连接池并保持 TCP 长连接；在底层支持时启用 TCP_NODELAY。
- 对同一主机返回的多个地址进行轮换，IPv4/IPv6 采用先成功者优先的连接行为。
- CurseForge/Modrinth 使用与 PCL 对照测试一致的官方 CDN 候选，并保留现有可用镜像作为失败回退。
- BMCLAPI 仅用于其真实支持的 Minecraft、Forge、Loader 和 OptiFine 资源，不作为 CurseForge MOD 的伪镜像。

## 进度、取消与持久化

- 热路径只累积内存进度，界面事件合并为约 250 毫秒一次，恢复状态批量落盘。
- 开始、完成、失败、暂停和取消仍立即持久化并发送事件。
- 取消任务组时先标记共享取消状态，再中止请求、清理临时文件和实例目录；延迟事件不得复活已取消任务。
- 分段、切源和恢复不能重复累计进度。

## 代码边界

- `src-tauri/src/tasks/download.rs`：下载任务入口、候选生成和文件级传输。
- `src-tauri/src/tasks/download/` 或等价独立模块：调度器、源健康、分段状态和连接策略；避免继续把所有职责堆进单文件。
- `src-tauri/src/tasks/monitor.rs`：共享引擎生命周期、任务组取消和全局连接预算。
- `src-tauri/src/tasks/streams/handle.rs`：进度事件节流与状态持久化。
- `src-tauri/src/tasks/commands.rs`：按优先级创建任务组，不改变前端调用接口。

## 验证

1. 单元测试覆盖候选推进、冷却、速度样本互不污染、并发预算、分段范围和尾部优先级。
2. 本地模拟服务器覆盖慢首字节、持续低速、断流、HTTP 403/429/5xx、忽略 Range、错误 Content-Range、损坏哈希及备用源抢跑。
3. 回归 `.mrpack`、CurseForge、湾大整合包、Forge 运行库、取消后删除、暂停恢复和任务重启。
4. 对同一整合包执行三轮冷启动对照；单文件停滞超过十秒必须出现明确恢复动作，90% 到完成的尾部目标为 20 至 30 秒。
5. 执行 Rust 单元测试、`cargo check`、前端生产构建和 Windows release 构建，只封装便携实验版并记录 SHA-256。

## 交付门槛

- 三轮均一次完成，文件数量、大小和哈希正确。
- 不出现无原因重复选择同一 URL、正常连接误判慢源或单文件失败重启整个任务组。
- 中位总耗时不高于 PCL 对照的 1.2 倍；若受外部网络波动影响，至少必须证明聚合带宽、尾部时间和恢复次数显著优于当前实验版。
- 未达到门槛时只保留为本地诊断构建，不赋正式版号、不发布。
